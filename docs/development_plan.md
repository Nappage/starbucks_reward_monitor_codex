# Starbucks Reward 在庫モニター開発計画（Phase 0: 計画）

## 1. 目的
Starbucks Rewards の交換ページにおける以下2商品の在庫状態を継続監視し、
欠品状態の継続・在庫復活を検知できる最小機能を段階的に実装する。

- スターマグ ブラウン 296ml
- スターマグ グリーン 296ml

対象URL:
https://www.starbucks.co.jp/mystarbucks/reward/exchange/original_goods/

## 2. 開発方針

### 2.1 TDD（テスト駆動開発）
- Red: 先に失敗するテストを書く
- Green: テストを通す最小実装を行う
- Refactor: 振る舞いを変えずに改善する

### 2.2 ドキュメント駆動開発（Documentation-Driven Development）
- 実装前に仕様ドキュメントを更新する
- 仕様→テスト→実装の順序を守る
- 仕様変更は、必ず差分理由（背景・影響範囲）を記録する

## 3. スコープ（段階的実装）

### Phase 1: 最小在庫取得（MVP）
**目標**: 2商品について在庫状態を取得し、ログ出力できる。

実施項目:
1. 在庫ステータス取得用の入力（URL/商品名）仕様を定義
2. HTML取得（HTTPクライアント）
3. HTML解析で対象商品の在庫状態を判定
4. CLI実行時に時刻付きログを標準出力へ出す
5. 単体テスト（解析ロジック中心）
6. スモークテスト（1回実行）

### Phase 2: 永続化と差分検知
**目標**: 前回結果と比較し、変化時のみ通知可能にする。

実施項目:
1. 結果のローカル保存（JSON/SQLiteのどちらかを採用）
2. 前回比較ロジック
3. 「欠品→在庫あり」遷移を検知
4. テスト追加（状態遷移）

### Phase 3: 通知
**目標**: 在庫復活時に通知する。

候補:
- メール
- Slack Webhook
- LINE Notify互換方式（代替手段含む）

実施項目:
1. 通知インターフェース定義
2. 通知アダプタ実装（まず1つ）
3. 通知抑制（連投防止）
4. テスト追加（通知条件）

### Phase 4: 運用
**目標**: 定期実行し、障害時に再実行可能な運用を整える。

実施項目:
1. 実行スケジュール（cron/GitHub Actions）
2. リトライ/タイムアウト設計
3. 監視ログの整形
4. 運用Runbook整備

## 4. 受け入れ基準（Phase 1）
- 指定URLを取得できる
- 2商品名の在庫状態を判定できる
- 実行ログに「実行時刻・商品名・在庫状態」が出る
- 解析ロジックがfixtureベースのテストで再現可能

## 5. リスクと対策
1. ページDOM変更で解析不能
   - 対策: セレクタ集中管理、fixture更新手順を文書化
2. 一時的な通信失敗
   - 対策: タイムアウト・リトライ・失敗ログ
3. 利用規約/アクセス負荷
   - 対策: 過剰アクセスを避ける（低頻度ポーリング）

## 6. 初期タスクバックログ（次セッションで着手）
1. 技術選定メモ作成（言語、HTTP、パーサ、テストフレームワーク）
2. `docs/spec_phase1.md` 作成（入出力、判定ルール、エラー方針）
3. HTML fixture 収集方針策定
4. 最初の失敗テスト作成（商品名→在庫判定）
5. 最小実装でテストGreen化

## 7. Definition of Done（各PR共通）
- 仕様ドキュメント更新済み
- テストが追加/更新され全件パス
- ログ/エラー時の挙動が明文化されている
- 次セッションに引き継げるメモを残している
